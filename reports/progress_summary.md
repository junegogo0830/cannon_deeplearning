# 진행 상황 정리 (조원 공유용)

> 이 문서는 지금까지 한 작업을 조원들이 따라올 수 있게 정리한 것입니다. 세부 근거/수치는 `reports/eda_summary.md`와 `data/processed/eda/*.csv`에, 실제 코드는 `src/`, `scripts/`에 있습니다.

## 1. 과제 요건 (재확인)

- 기종별 이미지 입력 → 15개(기종마다 실제로는 13~20개) 스텝 각각 PASS/FAIL을 threshold 방식으로 판정
- FAIL 데이터 극소 → **이상탐지(anomaly detection)** 접근
- GPU 없음 → CPU 경량 접근
- YOLO/OCR/템플릿매칭 등 기성 알고리즘 **결과를 그대로 판정에 쓰지 않음** — 스코어링·threshold는 직접 구성

## 2. 데이터 실체 파악 (EDA)

**구조**
```
data/raw/<기종코드>/<제품시리얼>/step_N.jpg          # N=0부터, 기종마다 스텝 수 다름
data/raw/<기종코드>/<제품시리얼>/NG/<timestamp>_..._step_N.jpg   # 불량으로 확인된 스텝의 원본 샷
```
- 라벨 CSV는 없음. **`NG/` 폴더의 존재·파일명이 FAIL 라벨의 유일한 소스**
- 기종코드(예 `3029C003AA`)는 마케팅 모델명이 아니라 생산주문(대오더) 코드. 제품 시리얼 앞 3글자와 1:1 대응
- 해상도 전수 확인 결과 1024×768로 완전히 동일

**극심한 불균형 (재확인)**
- 전체 3,214개 제품 중 FAIL 라벨 있는 건 **9개(0.28%)**
- 13개 기종 중 **3개(3029C003AA, 3029C004AA, 3029C009AA)에만** FAIL 존재 → 나머지 10개 기종은 정량 평가 자체가 불가능

**핸디형 카메라 편차 (실측)**
- 스텝마다 편차 성격이 다름 — 이동 최대 150px, 회전 최대 20~30°
- 같은 스텝이어도 "왜 정렬이 어려운가"가 다름: 대칭적/반복적 구도라 매칭이 헷갈리는 유형(예: 네 귀퉁이 대각선 지지대) vs 조명/노출 변동이 큰 유형 — 이건 섞어서 얘기하면 안 됨(하나는 촬영 프로세스 노이즈, FAIL과 무관)

**xlsx(`T595NP_층별일람표_2.xlsx`) 체크포인트 매핑**
- `화상검사Point` 시트: 기종별로 각 체크포인트(①~⑮)가 어떤 부품/라벨을 보증하는지 정리돼 있음
- **체크포인트 번호 N = `step_(N-1).jpg`** 라는 대응관계를 실제 FAIL 3건과 교차검증해서 확인함(예: step2 결함="Canon 인쇄 누락" ↔ 체크포인트③="우전카바 인쇄, 인쇄상태 확인")
- 3029C003AA 15개 체크포인트 중 **13개(13, 15번 제외)에 보증 항목이 있음** (`data/processed/eda/xlsx_checkpoint_map.csv`). 항목 없는 건 13번, 15번뿐
- **15번 체크포인트(=step14)는 우리 3개 FAIL기종(3029C003AA, 3029C004AA, 3029C009AA) 전부에서 항목이 없음** — "무슨 부품/라벨을 보는지" 문서 스펙이 없는 스텝 (3029C010AA에선 15번이 ADF 원고적재 라벨로 따로 있음 → 체크포인트 번호의 의미가 기종마다 다름). 실제 FAIL 2건을 열어보니 노치(이음새) 부위 미세한 갭 차이였음(정상 6장과 대조해서 확인) — 근데 이건 문서 근거가 아니라 우리가 육안으로 관찰한 패턴임(표본 2개, 일반화 주의)

## 3. 전처리 (실제 코드 기준)

모든 방법이 공통으로 거치는 입력 처리와, 방법별로 다른 특징 추출을 나눠서 정리했어요.

**3-1. 공통 입력 처리**

| 단계 | 내용 | 코드 |
|---|---|---|
| 이미지 로드 | BGR 컬러로 읽음. 한글 경로 문제 때문에 `cv2.imread` 대신 `np.fromfile` + `cv2.imdecode` 사용 | `src/data/dataset.py::read_image` |
| ROI 크롭 | **현재 미지정 (`roi=None`, 전체 프레임 사용)**. 노치/라벨 부위 ROI는 아직 정하지 않음 | `src/data/preprocess.py::crop_roi` |
| 리사이즈 | 원본 1024×768 → **384×512** (4:3 유지, 절반). `INTER_AREA` 보간 | `preprocess.py::resize_image` |
| 입력 크기(AE 실험) | 96×128 (CPU 속도 + 16의 배수 조건) | `scripts/compare_ad_methods.py` |

**3-2. 정렬 (지금은 기본 경로에서 빠짐 — 실험에 따라 on/off)**

ORB 특징점(1500개) → Hamming 매칭(상위 200쌍) → `estimateAffinePartial2D`(RANSAC, 재투영 임계 5px, 4자유도: 이동·회전·등방배율) → **이중 게이트 통과시만 워프 적용**
- 매칭 게이트: inlier ≥ 15개 & inlier 비율 ≥ 0.25
- 타당성 게이트: |dx| ≤ 200px, |dy| ≤ 150px, |회전| ≤ 20°
- 실패 시 정책(`alignment.on_failure`): `exclude`(제외) / `keep_unaligned`(원본 그대로 진행)
- homography(8자유도)는 쓰지 않음 — 매칭이 부실할 때 과적합해서 오히려 악화됨(실험으로 확인)

**3-3. 방법별 특징 추출**

| 방법 | 특징 | 세부 |
|---|---|---|
| handcrafted (`config.yaml`) | 패치 25차원 | 그래디언트 방향 히스토그램(9빈, 크기 가중) + 채도가중 Hue 히스토그램(12빈) + 텍스처 통계(그레이 평균·표준편차, 라플라시안 평균절대값·표준편차). **밝기 원값은 직접 안 씀** (조명 노이즈 배제 목적) |
| 패치 분할 (handcrafted) | 64px, 128px 두 스케일 | stride 32, 가장자리 패치는 안쪽으로 당겨서 잘림 방지 |
| CNN (`config_cnn.yaml`) | MobileNetV3-Small (ImageNet 사전학습, **frozen**) | BGR→RGB, /255, ImageNet mean/std 정규화. 한 번의 forward로 layer 4(40ch, 24×32=768 위치)와 layer 9(96ch, 12×16=192 위치)를 동시에 추출. 각 공간 칸 = 하나의 패치 |
| PaDiM (비교) | CNN layer 4 | 위치별 평균·공분산(정규화 1e-2·I), 마할라노비스 거리 |
| AutoEncoder (비교) | 원본 픽셀 96×128 | RGB [0,1], MSE 재구성, 스코어 = 재구성오차 상위 5% 픽셀 평균 |

**3-4. 학습/검증 분할 (중요: 전처리 순서가 결과를 좌우함)**
- PASS 목록(`step_N.jpg` 전부)을 seed 42로 섞음
- **val을 먼저 떼어냄**: max(min_val=150, 전체의 20%)장 — threshold 산출 전용
- 나머지에서 `max_train`(실험에선 60장)만 뱅크 학습에 사용
- 이 순서를 바꾸면 안 됨: 예전에 max_train을 먼저 자르고 나서 20%를 val로 떼는 바람에 val이 8~12장이 됐고, threshold가 엉터리가 됐음 (5-1 참고)

**3-5. 라벨/합성 결함**
- 라벨 CSV 없음. PASS = 루트의 `step_N.jpg`, FAIL = `NG/` 폴더 이미지
- 합성 결함(cutout / 밝기 저하 / 패치 복사-이동)은 현재 **원본 이미지에 주입한 뒤 전처리·정렬을 거침** — 주입된 결함이 정렬 자체를 깨뜨릴 수 있어서, 엄밀히는 "정렬된 이미지에 주입"으로 바꿔야 스코어링만 따로 평가할 수 있음 (미수정, 한계로 기록)

**3-6. 실행 환경 주의**
- Windows에서 `cv2/numpy/pandas`를 먼저 import한 뒤 `torch`를 import하면 `c10.dll` 로드 실패가 남. 진입 스크립트(`train/evaluate/infer/compare_ad_methods`)는 **`import torch`를 맨 위에** 둬야 함

## 5. 실험하면서 알아낸 것 (중요도 순)

### 5-1. threshold 계산용 검증(val) 표본이 너무 작으면 전부 거짓말이 된다
- 처음엔 val이 8~12장이었는데, 이걸로 99퍼센타일 threshold를 잡으면 사실상 "12개 중 제일 큰 값 근처"라 실제 정상 모집단(900장)의 꼬리 분포를 전혀 대변 못함
- `min_val=150`으로 val을 따로 넉넉히 확보하도록 고침(`src/data/split.py::reserve_val_then_train`) → FPR이 11~19% → **0.8~4%대의 믿을 만한 수치**로 정상화됨
- **교훈: 지표(FPR, "캐치했다")를 볼 때 threshold가 몇 장으로 산출됐는지부터 확인할 것.**

### 5-2. 정렬(alignment)을 어떻게 다룰지 — 세 가지를 다 실험함
| 정책 | 결과 |
|---|---|
| 강제(실패시 제외) | 데이터 손실 큼(스텝에 따라 최대 55% 제외). "실제FAIL 캐치"의 상당수가 **정렬이 우연히 실패해서 자동 FAIL 처리된 부작용**이었음(설계된 메커니즘 아님) |
| 완화(soft, 실패해도 원본으로 진행) | 데이터 손실 없음. 정렬 잘 되던 스텝에선 오히려 성능 개선(AUROC↑, FPR↓) |
| **아예 안 함** | 뚜렷한 결함(라벨 누락)조차 못 잡기 시작함 — "빈 표면"이 있어야 할 자리에 있든 없어야 할 자리에 있든 위치정보가 없으면 구분이 안 됨 |

→ **결론: 정렬은 시도하되 강제(hard gate)하지 않는 게 최적.** 완전 제거는 과했음.

### 5-3. 스텝마다 정렬 신뢰도가 다르고, 원인도 다르다 (3029C003AA 기준)
- 정렬 양호: 2, 3, 4, 8, 9, 10 (6개) — 실제 FAIL 있는 2, 9 둘 다 검증: FPR 2% 내외, 실제 FAIL 정상 캐치
- 정렬 요주의: 0, 1, 5, 6, 7, 11, 12, 13, 14 (9개) — 근데 이 9개도 하나의 원인이 아님:
  - 대칭구도 혼동형(0,6,12,14): ORB가 자신있게 틀린 변환을 냄
  - 조명 지배형(7): 정렬 자체보다 밝기 변동(정상 이미지 기준 std 21.5, 제일 큼)이 문제 — **이건 FAIL 특성이 아니라 촬영 프로세스 노이즈임, 헷갈리지 말 것**
  - 저텍스처형(11,13): 매칭점은 적지만 이동량 자체는 작음
- **9개 중 실제 FAIL 데이터가 있는 건 6, 7, 14뿐.** 나머지 6개(0,1,5,11,12,13)는 정렬이 불안정하다는 것만 알 뿐 결함이 어떻게 생기는지 전혀 모름 → 이 6개에 대해 뭔가 만들면 그건 근거 없는 추측이 됨(주의).

### 5-4. patch_knn(핸드크래프트) vs 사전학습 CNN 임베딩
- CNN(MobileNetV3 frozen, 특징 추출기로만 사용) + soft-align: 정렬 잘 되던 스텝에서 AUROC↑, FPR↓. 정렬 어려운 스텝은 개선 안 됨 — CNN이 만능은 아니었음.

### 5-5. step14 국소 접근(템플릿매칭으로 노치 위치 찾기) — 1차 실패, 교훈은 남음
- 타이트한 템플릿 + 탐색범위 제한 + 회전탐색으로 8장 중 6장(75%) 위치는 찾음(ORB 전체정렬 45%보다 나음)
- 근데 찾은 위치에서 **그레이스케일 픽셀 차이(MAD)로 비교했더니 PASS/FAIL이 안 갈림** — 원인: 조명/반사가 여전히 지배적. 처음에 만든 "일루미네이션 강건 특징(엣지방향·채도가중Hue)"을 이 국소 비교에도 재사용해야 했는데 빼먹고 raw MAD를 씀. **교훈이 있었는데 딴 데서 또 까먹은 사례 — 다음에 국소 비교 다시 시도할 땐 handcrafted 특징으로 할 것.**

### 5-6. patch_knn vs PaDiM vs AutoEncoder 3파전 비교 (완전 무정렬 조건)
| | AUROC (step2/14) | 비고 |
|---|---|---|
| **patch_knn** | 0.80 / 0.74 | 최고 성능 |
| padim | 0.75 / 0.71 | 근접, 위치별 가우시안이라 이론상 정렬 없인 더 나빠야 하는데 생각보다 안정적 |
| autoencoder | 0.25 / 0.34 | **무작위보다 못함** — 학습표본(60장) 부족 + 96×128로 줄이면서 미세결함이 소실된 것으로 추정 |

→ **AE는 이 문제(표본 극소 + 미세결함)엔 안 맞는다는 근거 확보.**

## 6. 지금 상태를 한 줄로 요약하면

**어떤 방법(handcrafted/CNN/PaDiM/AE)을 쓰든, 어떤 정렬 정책을 쓰든 — "뚜렷한 결함(라벨 누락 등)"은 낮은 오탐률(1~4%)로 꽤 잘 잡히고, "미묘한 결함(이음새 미세갭, 라벨 텍스트 오차)"은 아직 못 잡는다.** 이건 알고리즘 선택 문제가 아니라, 스텝당 실제 FAIL 예시가 1~2개뿐이라 신뢰도 있게 튜닝/검증할 수 없다는 **데이터 자체의 한계**로 보임 (네 가지 방법론을 교차검증해서 일관되게 나온 결론이라 근거는 탄탄함).
